I2C works like that. The ESP32 speaks on shared wires, says an address, and the device with that address responds.

ConceptI2C Is a Shared Conversation Bus

A protocol is a rulebook for communication. It defines who talks, when they talk, how bits are timed, and how the receiver knows the message is meant for it.

I2C uses two signal wires. SDA carries data. SCL carries the clock. The ESP32 usually controls the conversation, and the connected modules respond when their address is called.

Older tutorials often say master and slave. You will still see those words in datasheets and library code. A clearer modern way to say the same idea is controller and peripheral. In this mission, the ESP32 is the controller. The OLED and BME280 are peripherals.

Engineering Explanation

The ESP32 needs protocols because raw wires are not enough. A GPIO can be HIGH or LOW, but a display or sensor needs structured information: start here, send this address, write this command, read these bytes, stop now.

I2C solves that with a bus. The bus is shared by all connected I2C devices. The controller pulls the clock line to create timing. The data line changes in sync with that clock. At the start of a transaction, the controller sends a device address. Only the peripheral with that address should respond.

This is why the OLED and BME280 can both use GPIO21 and GPIO22 in this mission. GPIO21 and GPIO22 are the common Arduino ESP32 example pins used across this site, but ESP32 I2C pins are configurable in code when Wire.begin(SDA, SCL) matches the wires.

They are not connected to private signal wires. They share the same bus, but they use different addresses. The OLED might answer at 0x3C or 0x3D, while the BME280 might answer at 0x76 or 0x77. If two devices have the same fixed address on one bus, the ESP32 cannot reliably choose between them without changing an address or adding extra hardware such as an I2C multiplexer.

I2C lines normally rest HIGH because of pull-up resistors. Devices communicate by pulling the lines LOW at the right times. Many breakout modules already include pull-up resistors, which is why beginner circuits often work without adding extra resistors. But if the wires are long, the modules are many, or the pull-ups are missing or too strong together, the bus can become unreliable.

I2C is excellent for short, low-pin-count communication inside a project. It is not the best choice for long cables, very high speed, or devices that all have the same fixed address.

For this classic ESP32 circuit, use documented 3.3 V-compatible I2C breakouts and pull SDA/SCL up to 3.3 V. A regulator on a module does not prove its bus is level shifted. Check where onboard pull-ups connect before powering a module at 5 V; use suitable bidirectional I2C level shifting if the bus levels differ. The ESP32 internal pulls are weak and should not replace appropriate external bus pull-ups. For a short 100 kHz breadboard bus, 4.7 kOhm on each line is a common starting point when none are fitted; verify rise time/loading for your circuit rather than adding another pair blindly. Parallel module pull-ups reduce the effective resistance.

The scanner prints 7-bit addresses, not the shifted 8-bit read/write bytes some datasheets show. A response at 0x76/0x77 can come from BME280 or BMP280; compare the chip-ID register and module documentation in the BME280 guide. A response at 0x3C/0x3D does not establish OLED controller or dimensions. Two devices sharing an address may appear as one response; isolate modules to diagnose collisions.

Real WorldReal-World Analogy

Think of I2C like an apartment building intercom. Everyone is connected to the same intercom system, but the visitor presses one apartment number. Only that apartment should answer.

SDA is the spoken message. SCL is the rhythm that keeps the message understandable, like a metronome.

The address is the apartment number. Without the address, every device would hear noise and nobody would know who should respond.

⌨️Arduino Code

Copy this into Arduino IDE, then click Upload.

i2c_scanner_esp32.ino 
#include <Arduino.h>
#include <Wire.h>

constexpr int I2C_SDA = 21;
constexpr int I2C_SCL = 22;

void setup() {
  Serial.begin(115200);
  delay(1000);
  if (!Wire.begin(I2C_SDA, I2C_SCL, 100000)) {
    Serial.println("I2C initialization failed: check board and pin selection.");
    while (true) delay(1000);
  }
  Wire.setTimeOut(50); // Milliseconds per transaction, not the scan interval.
  Serial.println("I2C scanner: SDA GPIO21, SCL GPIO22, 100 kHz");
}

void loop() {
  unsigned int found = 0;
  unsigned int faults = 0;
  for (uint8_t address = 0x08; address <= 0x77; ++address) {
    Wire.beginTransmission(address);
    const uint8_t status = Wire.endTransmission();
    if (status == 0) {
      Serial.printf("ACK at 7-bit address 0x%02X (identity not checked)\n", address);
      ++found;
    } else if (status != 2) { // 2: address NACK; no response at this address.
      Serial.printf("Bus error %u at 0x%02X\n", status, address);
      ++faults;
    }
  }
  Serial.printf("Scan: %u responding address(es), %u bus error(s)\n", found, faults);
  if (found == 0) Serial.println("Check power, common GND, pins and pull-ups.");
  delay(5000);
}

This scanner tests non-reserved 7-bit addresses 0x08–0x77. An ACK proves only that something answered at an address: it does not identify an SSD1306, BME280 or BMP280, validate all wiring, or prove measurement/display operation. Use the device-specific guide next. Do not scan a bus containing parts whose datasheet prohibits this probe.

CodeLine-by-line Explanation

  • Wire.h gives the ESP32 Arduino core its I2C functions.
  • I2C_SDA is set to GPIO21, the common ESP32 SDA example pin used in this mission.
  • I2C_SCL is set to GPIO22, the common ESP32 SCL example pin used in this mission.
  • Serial.begin(115200) starts Serial Monitor so you can see the scan results.
  • Wire.begin(I2C_SDA, I2C_SCL, 100000) checks initialization on the declared pins at 100 kHz; setTimeOut(50) bounds each transaction in milliseconds.
  • The loop probes non-reserved 7-bit addresses 0x08 through 0x77, skipping reserved address blocks.
  • Wire.beginTransmission(address) prepares a message to one possible address.
  • Wire.endTransmission() sends the address and returns an error code.
  • If the error code is 0, a device answered at that address.
  • The sketch reports ACKs without inferring identity. Use the component documentation and initialization checks after scanning.

OutputExpected Behaviour

Illustrative output, not a recorded hardware result:

I2C scanner: SDA GPIO21, SCL GPIO22, 100 kHz ACK at 7-bit address 0x3C (identity not checked) ACK at 7-bit address 0x76 (identity not checked) Scan: 2 responding address(es), 0 bus error(s)

Your addresses may differ. 0x3C/0x3D are common OLED addresses; 0x76/0x77 can belong to BME280 or BMP280. Confirm controller, sensor and interface using their documentation and component-specific initialization. The count is responding addresses, not necessarily physical devices. An ACK does not prove that a display works or sensor data is valid.

Status 2 is an address NACK, normally expected at unused addresses. Other statuses are reported as bus errors; status 5 means a transaction timeout on the reviewed ESP32 Wire implementation. Check power and common ground, shorten wires, inspect pull-ups and isolate one module. A stuck-low line can produce repeated timeouts; disconnect power before rewiring.

MistakesCommon Mistakes

  • Swapping SDA and SCL

    The clock and data lines have different jobs.

  • Forgetting common ground

    The ESP32 and modules need the same voltage reference.

  • Using a non-I2C OLED

    Some displays use SPI and have more pins.

  • Expecting all BME280 modules to use the same address

    Module boards can configure the address pin differently.

  • Two devices share the same fixed address

    I2C addresses must be unique on one bus.

  • Using long jumper wires

    I2C is sensitive to wiring length, capacitance, and weak pull-ups.

  • Thinking the scanner reads sensor data

    The scanner only checks whether a device answers at an address.

  • Ignoring address output

    Copying a tutorial address without checking the real module can cause blank screens or failed sensors.

!Troubleshooting

Most ESP32 problems are wiring, power, library, or timing issues. Check these first.

  • Scanner prints no devices

    Likely cause: Power, ground, SDA, SCL, or pin selection is wrong.

    Fix: Check 3.3 V, GND, GPIO21, GPIO22, and make sure Wire.begin(21, 22) is used.

  • Only the expected OLED address appears

    Likely cause: The other module may be unpowered, wired incorrectly, in SPI mode or at a different address.

    Fix: Identify the responding module by testing one at a time. Check BME280 power, CS/SDO straps and SDA/SCL labels; do not infer sensor identity from the scan.

  • Only an address at 0x76/0x77 appears

    Likely cause: The OLED may be unpowered, on another address or interface, or incorrectly wired.

    Fix: Check OLED VCC, GND, SDA to GPIO21, and SCL to GPIO22.

  • Addresses appear sometimes but disappear later

    Likely cause: Loose breadboard wires, long wires, or weak pull-ups can make the bus unstable.

    Fix: Shorten wires, reseat jumpers, and test one module at a time.

  • Code uploads but Serial Monitor shows unreadable text

    Likely cause: Serial Monitor baud rate does not match the sketch.

    Fix: Set Serial Monitor to 115200 baud.

TipEngineer Tip

Before debugging a complex display or sensor program, run an I2C scanner. It separates wiring problems from code problems. If the scanner cannot see the device, a bigger library example will not fix the hardware connection.

It is one shared conversation where each device answers only when its address is called.

?FAQs

  • What is a communication protocol?

    A communication protocol is an agreed set of rules for how devices send and receive information. Without a protocol, the ESP32 and a sensor would not know how to understand each other.

  • What does I2C mean?

    I2C means Inter-Integrated Circuit. It is a two-wire communication bus used by many displays, sensors, clocks, memory chips, and small modules.

  • Which pins does ESP32 use for I2C?

    This site's ESP32 DevKit examples use GPIO21 as SDA and GPIO22 as SCL. ESP32 I2C pins can be changed in code, but the wiring and Wire.begin(SDA, SCL) call must match.

  • What is SDA?

    SDA is the data line. It carries the bits that represent addresses, commands, and data.

  • What is SCL?

    SCL is the clock line. It provides timing so devices know when each data bit should be read.

  • What is an I2C address?

    An I2C address is a small number that identifies one device on the bus. The ESP32 sends the address first so only the selected device responds.

  • Why can multiple devices share SDA and SCL?

    They can share the wires because each device listens for its own address. The ESP32 talks to one addressed device at a time.

  • What address does an SSD1306 OLED usually use?

    Most SSD1306 0.96 inch OLED modules use 0x3C. Some use 0x3D.

  • What address does a BME280 usually use?

    Many BME280 modules use 0x76 or 0x77 depending on the module wiring.

  • What is an I2C scanner?

    It probes addresses and reports acknowledgements. An ACK does not identify the chip, confirm OLED dimensions, or prove valid sensor readings. Different chips can use the same address.

  • Do I need pull-up resistors for I2C?

    Yes, I2C needs pull-up resistors on SDA and SCL. Many breakout modules already include them, but long wires or many modules can still cause problems.

  • Can I use 5 V I2C modules with ESP32?

    Module supply and signal voltage are separate. ESP32 SDA/SCL must not be pulled up to 5 V. Verify module pull-up connections and use suitable bidirectional I2C level shifting when required; a regulator alone does not prove compatibility.

  • Why does the scanner show no devices?

    The most common causes are missing power, missing ground, swapped SDA/SCL, wrong pins, or a module that is not I2C.

  • Can two I2C devices have the same address?

    Not on the same bus unless you use extra hardware such as an I2C multiplexer or can change one device address.

  • Is I2C good for long cables?

    I2C is best for short connections on the same board or inside the same small device. Long wires can make the signals unreliable.
